The fuzz `messages` target now asserts that whatever parses survives encode and decode unchanged; local run 30 s, 2.2 million runs, no failure. The UI type check found that the Performer screen has no state for `HandingOver` or `Finished`: `performerPhase()` folds them to Playing and Idle (test added). `docs/adr/ADR-011-architecture-rule-changes.md` (Proposed) records the three rule changes made without an ADR. - Bugfix PR #32, Windows-only flake in the link tests: `a_panicking_handler_rejects_the_command_and_keeps_the_connection` failed intermittently on Windows CI (3 runs on `main`, never on a PR run, never reproduced). The test now gives its client a 4 s `dead_after` instead of 600 ms, and `expect` lists the events it skipped when one is missing. No production code changed. The cause is a hypothesis: a slow first panic stalls the connection thread past `dead_after`, the client reconnects and the Ack is lost. If it fails again, the skipped list shows whether a `Disconnected` came first. Possible production concern: handlers run on the connection thread, so a slow handler blocks pings.
- WP 2.6 Setlists, PR #27: `crates/setlists` has `Setlist` (id, name, ordered `Entry`s of `EntryId` + `SongId`, `Revision`), `Edit` (`Rename`, `Add { song, at }`, `Remove`, `Move { entry, to }`), `SetlistEvent` (`Renamed`, `EntryAdded`, `EntryRemoved`, `EntryMoved`), `Rejection`, `InvalidSetlist`, and the `SetlistRepository` trait with `InMemorySetlistRepository` (optimistic: `save(setlist, expected)`, `delete(id, expected)`, `SaveError::Stale`). One entry point, `Setlist::edit(expected_rev, edit)`: a stale revision is refused, a refused edit changes nothing, every accepted edit raises the revision by exactly one; no-op edits (same name, move to the same index) are refused so the revision never rises for nothing. Entry ids are unique and never reused, also after `restore`. Entries whose song is gone stay editable; `dangling(is_known)` reports them (SPEC: validate on activation, not on edit). `SongId` moved from `catalogue` to `shared-kernel` (SPEC §14.1) because `setlists` may only depend on `shared-kernel`. 13 tests: 11 scenarios and 2 property tests (2000 cases each: the setlist stays valid under any edit sequence incl. stale ones; each event matches the change it reports). Checked that the properties can fail: allowing a move to the same index fails both the scenario and the property, which shrinks. Not yet: `SetlistCreated`/`Deleted` events (they belong to the repository use case), serde and the ExtState schema (WP 3.7), the v1 import (WP 4.8), `PlannedSong` building from a setlist (WP 2.7/2.8).
- WP 2.5 Property tests, PR #26: `proptest` (dev-dependency of `performance` only). `performance_properties.rs`: random setlists (0-5 songs, contiguous or gapped, hard stops) and random input sequences (up to 120 inputs, 2000 cases); invariants after every step: index in range, last Play/Pause effect matches the phase, `SetCountIn(true)` only while counting in with the flag on, every `SeekTo` >= 0, a refused command changes nothing, ticks do nothing while nothing runs and move at most one song, at most one hand-over per step and never closer than the 1 s debounce, finish and hard stop always end with `Pause`. Also: playing straight through visits every song once in order and finishes once; Finished stays Finished under any ticks. `count_in_properties.rs`: any valid tempo map and cue (5000 cases): lead-in finite, in [0, cue], monotonic in bars, exact bars x bar length in a constant tempo. Checked that the properties can fail: with the debounce removed they fail and shrink to a 2-song counterexample. No bug found in the state machine. Found while writing them: a hand-over whose position never lands inside the next song stays in `HandingOver` forever (already listed under Not yet, no retry or timeout).
- WP 2.4 Count-in and tempo maths, PR #25: `crates/performance` has `TimeSignature`, `TempoSegment`, `TempoMap` (snapshot, walks back through tempo and signature changes), `CountIn` (default 2 bars as in v1) and `InvalidTempoMap`. `CountIn::lead_in(map, cue, !bpm)` gives the `lead_in` for `Input::SeekCue`; `!bpm` wins over the map and uses the signature at the cue; never longer than the cue. Assumption to verify against REAPER in WP 3.x: the tempo counts quarter notes per minute, so 6/8 at 120 is a 3 s bar. Not yet: building the `TempoMap` from REAPER (the port, WP 2.7).
- WP 2.3 Performance state machine, PR #24: `crates/performance` is a pure `Performance::step(Input) -> Output { effects, events }` (no I/O, clock injected as a value in `Input::Tick`). Phases `Idle, Playing, Paused, CountingIn, HardStopped, HandingOver, Finished`. Inputs: `Tick, Play, Pause, Next, Previous, RestartSong, Seek, SeekCue, SetFlag`. Effects for the adapter: `Play, Pause, SeekTo, SetCountIn`. Events: `PerformanceStarted, HandOverStarted/Completed, HardStopReached, PerformanceFinished, FlagChanged, SeekPerformed, CommandRejected`. `HandOverPolicy` (15 ms lead from ADR-005, 1 s debounce from v1). 27 scenario tests (hand-over contiguous and over a gap, one hand-over per song end, debounce, hard stop with `!length`, finish is terminal until Play, autoplay on Next, count-in on cue jumps only, pause cancels count-in). The crate may not depend on `catalogue` (architecture rule), so it has its own `PlannedSong { song_id, window, hard_stop }`; the extension builds it from `Song` and `Directives`. Not yet: reading REAPER's play state (an external pause or stop is not noticed), a position that leaves the song window while playing, a hand-over that never completes (no retry), who toggles REAPER's count-in around the click (v1 used action 40363 to enable it; confirm in WP 3.x), property tests (WP 2.5). `performance.rs` is 329 lines, slightly over the guideline.
- WP 2.1 + 2.2 Catalogue domain and directive grammar, PR #23: `crates/catalogue` has `Song` (window, effective length), `SongId` (region GUID), `Cue` (marker, name parsed once), `MarkerName` (tokenise and classify), `Directive` (`!1008`, `!length:N`, `!bpm:N`), `Directives` (first `!length` and first `!bpm` win, any `!1008` counts), `InvalidSong`; one type per file. Shared vectors in `testing/vectors/markers.json` (48: every v1 combination in any order, SWS-style `!<digits>` commands, malformed numbers, empty names). Not yet: domain events, `!bpm` read at the song's start edge from the tempo map (needs the port, WP 2.7), the catalog message, the Help-screen marker helper. v1 had no vectors, so parity is by reading v1 `markerUtils.ts`, not by replaying its tests.
